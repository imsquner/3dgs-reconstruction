## 一、S0 环境收尾

**目的**：让"加载模型 → 渲染 → 保存"这条链在本机完全可用，再去碰训练。

- [ ] `pytorch3d` 编译（进行中，20–40 分钟；`FORCE_CUDA=1`、`TORCH_CUDA_ARCH_LIST=8.9`、`MAX_JOBS=2`）
- [ ] 装训练依赖：`ultralytics`、`evo`、`torchmetrics`、`lpips`、`rich`、`seaborn`、`imgviz`、`wandb`
- [ ] `pretrained/yolov9e-seg.pt` 下载（GitHub，约 200 MB）
- [ ] `pretrained/raft-things.pth` 从本地 `医学三路线复现` 项目复制（21,108,000 字节）
- [ ] **总验收门**：本机渲染 frame 0/100/200/250，与包内 `after_opt` 对比，中位 PSNR ≥ 30 dB

**为什么先验渲染**：训练要跑几小时，如果渲染路径本身有偏差，训练结果再好也没法判断对错。渲染对上，等于把"模型加载 + 位姿 + 投影 + 光栅化"四件事同时钉死。

**风险**：pytorch3d 编译失败 → 用 `MAX_JOBS=1` 重试或降级到 pytorch3d 0.7.5；仍失败则训练链路受阻，先做网页（网页只需要渲染，但渲染也依赖它，见问题留存）。

## 二、S1 探路（30 帧）

**目的**：用最低成本暴露 OOM、速度、保存/重载问题。

- 配置：`工程/配置/walking_xyz_30f_local.yaml`（start=0, end=30）
- 命令：`python slam.py --inherit_from configs/rgbd/tum/config.yaml --config <cfg> --eval --dynamic --exp_name=local30 --save_results=1 --interval 1`
- 记录：初始化耗时、每帧跟踪耗时、mapping 累计、精修耗时、峰值显存、高斯数变化
- 检查：`point_cloud.ply` + `offsets/iteration_81500/offsets.pth` 是否生成；能否在独立进程加载

**门**：无未解释异常、模型可重载、显存峰值 < 7.5 GB。

**决策点**：若 OOM 或峰值 > 7.5 GB → 提出新协议（减帧/降分辨率）交老板确认，**不擅自改**。

## 三、S2 主场（walking_xyz 298 帧）

- 新 run ID 从头跑，不加载旧包模型
- 保留官方迭代次数：tracking 100、mapping 50、颜色精修 1500
- 无缓冲日志 + 心跳（每 10–30 秒写一次：已完成/总帧数、高斯数、显存、最近更新时间）
- 断点：每完成一个阶段写 checkpoint（不支持真正的训练中断续跑，见问题留存）

**门**：ATE ≤ 3 cm、PSNR（官方掩码口径）≥ 20 dB、全帧渲染无缺帧、峰值显存有记录。

## 五、S4 网页演示

**架构**：本地 WebSocket 渲染服务 + 复用现有前端骨架。

- 后端 `server_render.py`：模型常驻 GPU；收到 `{t, 相机位姿}` → `render()` → JPEG
- 自适应分辨率：拖动 640×480，静止后 1280×960
- 前端：三步改造现有 `index.html`/`app.mjs`——换数据源、接轨道控制、接输入视频
- 画面：左侧 4D 视图，右上输入视频小窗，底部时间轴，右下指标面板，全屏/大屏按钮

**门**：
1. 拖拽时 ≥ 15 fps（低清档）
2. 网页渲染帧与离线渲染帧 PSNR ≥ 35 dB（证明同一路径）
3. 大屏模式 1280×960 正常
4. 轨迹覆盖范围有可视化标注

## 八、失败与降级策略

| 情况 | 处置 |
|---|---|
| pytorch3d 编译失败 | 降 MAX_JOBS/换版本；仍失败则网页与训练一起卡住，需换机器或容器 |
| 298 帧 OOM | 保留失败日志，提出减帧协议请老板确认 |
| 精修耗时过长 | 记录实测；不改迭代次数，除非老板同意 |
| 网页延迟过高 | 降分辨率、改增量更新、或退化为"预渲染轨道视频 + 视频播放" |
| 时间不够 | 优先保 S0–S2 + 网页最小版；S3 可后补 |
